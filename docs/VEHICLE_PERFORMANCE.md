# 车辆检测输入尺寸与预处理对比

日期：2026-10-27。以下全部是**短时内部评测**，不是正式验收；场景、热状态和相机帧率会显著影响
端到端 FPS，因此模型对比优先看推理 P50/P95，而不是单次分析 FPS。

## 1. 固定图片集

网络到 GitHub/HuggingFace 超时，无法下载 COCO/coco128。本报告使用：

- `.model-cache/bus.jpg`：手工标注 bus 框 `[0.010, 0.210, 0.980, 0.680]`；
- 同一图片的 0.80/0.60/0.40/0.25 缩放、深色版本，用于检查小目标召回；
- `.model-cache/zidane.jpg`：无车辆，用于检查车辆误报。

这是**单图 + 合成缩放**回归集，只能发现明显的尺寸敏感问题，不能替代真实道路数据集上的
召回率/精确率验收。

## 2. 离线速度与固定集结果

环境：Intel Core Ultra 7 155H，ONNX Runtime 1.20.1 CPU，单进程；模型均为 YOLO11n + 内置 NMS，
输出 `[1,300,6]` 归一化坐标。

| 输入 | 模型 MB | p50 ms | bus 分数 | bus IoU | 缩放/深色通过 | zidane 车辆误报 |
|---|---|---|---|---|---|---|
| 640 | 10.8 | 66.67 | 0.9399 | 0.9805 | 5/5 | 0 |
| 480 | 10.7 | 67.38 | 0.9239 | 0.9590 | 4/5 | 0 |
| 416 | 10.7 | 29.68 | 0.9036 | 0.9377 | 5/5 | 0 |
| 384 | 10.7 | 27.07 | 0.8768 | 0.9599 | 5/5 | 0 |
| 352 | 10.6 | 50.59 | 0.9031 | 0.9469 | 5/5 | 0 |
| 320 | 10.6 | 21.71 | 0.8595 | 0.9592 | 4/5 | 0 |

注：单进程桌面 p50 受 CPU 频率和模型执行顺序影响明显（352 的 50.59 ms 是异常值，按 GFLOPs
它应低于 416），只能看数量级；尺寸决策以固定集召回 + 真机 P50/P95 为准。416/384/352 都是
5/5，320 在 0.25 缩放样本漏检并在 0.40 样本把 bus 误分类为 car。

## 3. 合成管线基准（无相机）

为避免相机场景、曝光和热状态干扰，新增 debug-only `BenchmarkActivity`：生成 480×640 合成 YUV，
经 `FrameConverter` 旋转 90° 后直接送入生产 `PipelineCoordinator`，预热 3 帧、测量 30 帧。

```powershell
adb shell am start -n com.roadvision.roadsense/.BenchmarkActivity
adb shell run-as com.roadvision.roadsense cat files/benchmark.json
```

| 输入 | e2e FPS | e2e P50/P95 | 转换 P50/P95 | 推理 P50/P95 |
|---|---|---|---|---|
| 416 | 21.5 | 44.4/56.8 ms | 6.3/7.5 ms | 37.8/58.1 ms |
| 352 | **27.1** | **34.6/45.6 ms** | 6.3/6.8 ms | 28.2/40.3 ms |

- 352 的转换 + 管线达到 **27.1 FPS**，416 为 21.5 FPS；两者都超过 15 FPS。
- 352 同时保持固定集 5/5，且 P95 更低，因此选为默认候选。
- 416 的首次合成基准曾出现 12.4 FPS，复测为 26.2 FPS（不含转换），说明设备热状态仍会影响
  单次数字；相对排序和 30 帧 P50/P95 比单次 FPS 更可靠。
- 真机 352 只有 6.4 FPS 是**相机采集 11.2 FPS** 限制，不是模型管线只有 6 FPS；需要在稳定
  高帧率场景复测完整端到端。

## 4. 真机结果

设备：HONOR MLM-AN00，Android 17 / SDK 37，CPU 推理，短时手持。

| 配置 | 采集 FPS | 分析 FPS | 推理 P50/P95 ms | E2E P50/P95 ms | 备注 |
|---|---|---|---|---|---|
| 640，旧预处理/转换 | 7.8 | 7.1 | 230.9/294.3 | 530.6/721.4 | 单帧快照 |
| 416，新预处理 | 5.1 | 5.3 | 49.4/86.2 | 125.2/— | 场景较暗，采集受限 |
| 416，新预处理 + 融合转换 | 22.8 | 13.7 | 70.5/75.8 | 136.0/156.0 | 持续 30 秒；瞬时曾 15.4 |
| 416 + classical lane（每 3 帧） | 13.4 | 6.1 | 147.5/243.0 | 257.9/380.0 | 车道成为新瓶颈 |
| 352，仅车辆 | 11.2 | 6.4 | 52.9/157.1 | 111.7/289.0 | 实际检出 1 辆车（82%），采集受限 |
| 352，明亮场景，仅车辆 | 30.1 | **28.1** | 33.2/36.7 | 68.8/89.3 | 热状态 1，超过 15 FPS |
| 416，夜间多车，仅车辆 | 9.6 | 3.4 | 146.7/318.2 | 261.1/462.3 | 实际检出 5 辆；热状态 3，密集场景最差样本 |
| 320，仅车辆 | 11.2 | 8.2 | 48.5/161.4 | 119.7/315.4 | 采集帧率低，P95 抖动大 |

结论：

- 合成转换 + 管线上，352 为 **27.1 FPS**、416 为 **21.5 FPS**，都已超过 15 FPS；352 固定集
  5/5，P95 45.6 ms 也低于 416 的 56.8 ms，因此 **352 作为默认候选**，416 作为保守回退。
- 真机相机路径会被采集帧率限制：352 在明亮场景达到采集 30.1 / 分析 **28.1 FPS**、推理
  33.2/36.7 ms、延迟 83.1 ms，已超过 15 FPS；同一 352 在暗光场景只有采集 11.2 / 分析 6.4 FPS，
  416 简单场景持续 13.7 FPS、夜间多车 3.4 FPS。性能高度依赖场景亮度/热状态。
- 因此 **15 FPS 已在明亮场景的真实相机端到端复现**，但还不能宣称跨场景持续稳定达标；暗光、
  密集夜间和启用 lane 的场景仍是限制。
- 352 真机已经实际检出车辆（黄色框 + 82%），416 在夜间多车画面检出 5 辆（Track ID + 置信度
  35%–64%），说明车辆-only 的端到端链路、坐标映射和叠加层在真实画面内容上有效；这仍不等于
  道路数据集上的召回率验收。
- 真实密集/夜间场景会显著拖慢：416 同一设备在同一夜间画面只有 3.4 FPS、推理 P50 146.7 ms，
  热状态 3。**15 FPS 尚未在真实道路场景稳定复现。**
- 320 固定集召回从 5/5 降到 4/5，且 P95 抖动更大；没有真实数据集前不建议直接切换。
- 启用当前 classical lane 后整条流水线降到约 6 FPS；车道路径需要单独优化/降频，不能把
  车辆-only 的 21–27 FPS 管线数字当作完整感知 FPS。
- 采集帧率在 9–23 FPS 间波动，分析 FPS 常被采集端限制；模型对比必须以合成基准和推理
  P50/P95 为准。

## 5. 本轮代码改动

### TensorPreprocessor

- 预计算 letterbox 的 x/y 映射，去掉每像素除法；
- mean/std 融合为 `gain/bias`；
- NCHW/NHWC、RGB/BGR 分支移到循环外；
- 使用 `floor` 修正 letterbox 边界映射；
- 检测器复用 scratch FloatArray，减少每帧数 MB 的分配；
- 新增与参考实现逐元素对比、scratch 复用测试。

416 真机推理：约 **66.5/132.1 → 49.4/86.2 ms**。

### FrameConverter

- YUV→RGB 与旋转合并为一次遍历，去掉整帧中间 RGB 缓冲和第二次旋转拷贝；
- 2x2 块复用 U/V；
- 定点 YUV 系数，减少浮点运算；
- 新增与旧浮点算法逐像素对比、覆盖 0/90/180/270 度的测试。

416 真机 E2E：约 **125.2 → 108.3 ms**（瞬时），持续 30 秒 13.7 FPS。

### 合成基准

- 新增 debug-only `BenchmarkActivity`，把 YUV 转换与管线纳入同一可复现测量；
- 352：27.1 FPS，e2e P50/P95 34.6/45.6 ms；
- 416：21.5 FPS，e2e P50/P95 44.4/56.8 ms。

## 6. 限制与下一步

- 评测集是单图合成缩放，不是道路数据集；`coco128`/COCO 下载被网络阻断。
- 真机短时结果受热状态、场景亮度和相机帧率影响；需要固定视频、固定亮度、固定温度的正式基准。
- 当前权重是 AGPL-3.0 评测模型，`BLOCKED`，不可进入发布包。
- 下一步优先级：
  1. 对 classical lane 做耗时剖析与降频/ROI 优化，否则完整流水线仍只有约 6 FPS；
  2. 用真实道路视频/小数据集复测 352 与 320 的召回，再决定是否接受 320；
  3. 预处理已不是主瓶颈，继续压缩需要模型/运行时优化（更小模型或厂商 GPU/QNN）；
  4. 在稳定高帧率场景（固定视频/亮度）复测相机端到端，区分采集上限与管线上限。
