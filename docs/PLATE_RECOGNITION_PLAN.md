# RoadVision 车牌识别方案（暂缓开发）

## 0. 决策记录

-   **2026-10-27：车牌检测与 OCR 只做方案记录，暂不开发训练工程。**
-   理由：中文车牌识别权重与字库在可达渠道内没有现成资产，自建需要数据集许可确认与 GPU
    算力；当前优先级低于把车辆/车道链路、诊断口径与 15 FPS 基线做扎实。
-   本文件不代表车牌已实现。恢复开发时按第 6 节执行，**不另建仓库、不另起一个 App 工程**。

## 1. 现状：代码就绪，缺权重

车牌链路在代码里是完整的，缺的只是模型资产。

| 能力 | 实现位置 | 状态 |
|---|---|---|
| 车牌检测适配 | `OnnxPlateDetector` + `VehicleOutputDecoder`（`[1,N,6]`） | 已实现 |
| 四角矫正 / 拒识 | `PlateCropper`：投影矫正到 160×48，最小源宽 48 px，拉普拉斯方差阈值 55 | 已实现，阈值待真机标定 |
| OCR 限频 | `OcrScheduler`：按 Track ID 限制识别频率 | 已实现 |
| 识别 | `OnnxPlateRecognizer` + `CtcDecoder`：`[1,T,alphabet+1]`、`blankIndex` | 已实现 |
| 多帧融合 | `OcrTemporalFusion`：投票、`uncertain` 状态 | 已实现 |
| 车牌-车辆关联 | `PlateVehicleMatcher`：连续多帧几何一致才确认；未确认不落库 | 已实现 |
| 编排 | `PipelineCoordinator`：每 N 帧跑一次车牌；`plate` 与 `ocr` 必须成对 | 已实现 |
| 事件落库与展示 | Room v2 + 事件列表 | 已实现 |

**缺资产：** `models/plate/model.onnx`、`models/ocr/model.onnx`、OCR 字库（`alphabet` /
`blankIndex`）。本地评测清单里没有 `plate` / `ocr` 段，因此当前构建不会加载也不会产生车牌事件。

## 2. 为什么不能"先接检测再说"（事实：2026-10-27 检索）

-   流水线强制 `plate` 与 `ocr` 成对（`PipelineFactory` 的 `require`），只有检测模型时流水线
    直接拒绝启动，不会降级出半个能力。
-   可达镜像（`hf-mirror.com`、`gitee.com`）内：

| 检索对象 | 结果 |
|---|---|
| 中文车牌识别（CTC + 中文/字母数字字库）ONNX | 未找到。HF 上为 TroCR 印刷体、伊朗/欧洲车牌；Gitee 以"车牌识别""HyperLPR3"检索无结果 |
| HyperLPR v1（Apache-2.0） | 只有 Keras `.h5` 与 Caffe `.caffemodel`，无 ONNX，也无现成字库表 |
| 中文车牌检测 | HF 有 CCPD2019 微调的 DETR（`mgmayank18/detr_finetuned_ccpd2019`），可导 ONNX，但单独无意义 |

-   说明：ONNX 不等于许可干净；上述候选的权重许可、训练数据许可均未审查。

## 3. 三条路线

| 路线 | 产物 | 成本 | 主要风险 | 建议 |
|---|---|---|---|---|
| **A. 自建**：CCPD 微调检测 + 训练 CRNN | 2 个 ONNX + 字库 | 代码量小，算力与数据是瓶颈 | 数据集许可、GPU、精度需要迭代 | 恢复开发时的默认方案 |
| **B. 采购**商用车牌识别 SDK | 闭源 so/arr | 预算 + 商务周期 | 与"本地处理、可审计"取舍；绑定厂商 | 需要最快出货时考虑 |
| **C. 非中文牌占位模型** | 链路可跑 | 最低 | 识别结果无意义，易被误当成能力 | 只允许临时验证，禁止进发布构建 |

## 4. 路线 A 的范围界定（澄清：不是新项目）

-   代码全部放在本仓库 `tools/train_plate_ocr/`，属于"模型资产生产线"，不进 APK。
-   产物只有三个文件：`models/plate/model.onnx`、`models/ocr/model.onnx`、字库（写进清单）。
-   App 侧改动仅为清单条目与阈值，推理、矫正、融合、关联、落库代码不改。
-   明确不做：新 App、新仓库、云端服务、在线学习。

## 5. 前置条件（决定能否开工）

1.  **数据许可**：CCPD 约 12 GB，学术发布不等于商用授权，必须核实能否用于商用训练并归档证据。
2.  **算力**：CRNN 在 10 万张规模上纯 CPU 不可行（本机 22 核估计数十小时/轮），需要 GPU；
    子集（1–2 万张）可先做"能跑但精度一般"的版本。
3.  **字库**：省份简称 + 字母数字 + 新能源号牌规则（含 8 位）；字库许可独立于模型许可。
4.  **评测集**：必须留出独立验证集，避免自测自评。

## 7. 建议的验收指标（待冻结）

-   字符级准确率、整牌准确率（区分蓝牌/新能源 8 位）
-   车牌检测召回率与四角定位误差
-   车牌-车辆误关联率
-   场景：白天、夜间、逆光、倾斜 ≥30°、遮挡、远景小目标
-   OCR 单次推理 P50/P95，以及开启车牌链路后的端到端 FPS

## 8. 技术备忘：与现有契约的对接点

-   `PlateCropper` 固定输出 **160×48**；OCR 契约输入必须与这个宽高比一致（例如 160×48 或
    320×96），否则 letterbox 会引入拉伸或额外填充，直接影响识别率。若要改输入尺寸，需同时
    调整 `PlateCropper` 的 `outputWidth/outputHeight`。
-   识别输出为 `[1, T, alphabet.size + 1]`，末维包含 blank；`blankIndex` 必须与导出模型一致。
-   检测输出沿用 `[1, N, 6]`（`x1,y1,x2,y2,score,classId`，坐标归一化），当前实现只用轴对齐框，
  四角点由框推导；若改用带角点的模型，需要扩展 `Detection` 或增加专用解码器。
-   `PlateVehicleMatcher` 要求连续多帧几何一致，帧率过低（<5 FPS）时确认会更慢，需同步调整确认帧数。
